# 深大开源 OpenMV 视觉代码分析：时钟 / 滤波 / 采集帧数

日期：2026-11-13
来源：`Vesna-Eye/视觉代码.zip`（仅一个文件，389 行，OpenMV MicroPython 脚本）
解压副本：`_recon/shenzhen_vision/视觉代码/main_final.py`

## 0. 一句话结论

- **时钟**：脚本完全不配置传感器时钟/PLL，也没有 `sensor.set_framerate()`；实际用的是
  OpenMV 固件默认值（OV5640 XCLK 24 MHz，PLL `0x3036=0x64`/`0x3037=0x13`，PCLK≈80 MHz）。
  代码里的 `time.clock()` 只是帧率计时器，与硬件时钟无关。
- **滤波**：**没有任何时间滤波**（无 Kalman、无滑动平均、无预测、无 PnP）；只有空间上的
  ROI 跟踪（目标外扩 ±40 px）+ 最大面积 blob 选择 + 固定曝光/增益/白平衡。
  串口直接发原始 blob 矩形（7 字节），中心点/角度都由接收端计算。
- **采集帧数**：QVGA 320×240 RGB565 + `IOCTL_SET_READOUT_WINDOW(0, 700, 640, 480)`
  （把传感器读出窗口压到 640×480）→ 驱动算出 **HTS=1438、VTS=268** →
  单帧 **4.82 ms ≈ 208 fps**（传感器侧采集时序上限）。
  作为对照，OpenMV 默认全幅 QVGA 是 HTS=1716、VTS=1000 → 21.45 ms ≈ 46.6 fps
  （与 OpenMV 官方实测 RT1062/OV5640 QVGA 46.7 fps 一致）。

## 1. 硬件判定

脚本 `import sensor / time / pyb / mjpeg / os`，是 OpenMV 固件上的 MicroPython 程序。
其中 `sensor.IOCTL_SET_READOUT_WINDOW` 目前只有 OpenMV 的 **OV5640** 驱动实现
（openmv/openmv 的 `ov5640.c`；MT9V034 的同一接口在 2021 年仍是 feature request），
因此可确定其硬件是 **OV5640 的 OpenMV 板**（OpenMV H7 Plus / RT1062 一类）。

工作流程：上电后等 0x11/0x22（yaw/pitch，实际未使用）→ `sensor.sleep(True)`
（发射前待机）→ 等 0xAB 触发 → 唤醒并空转 snapshot 等 0x55/0xFF 模式字 →
阶段 1 检测/发送 → 切读出窗口 → 阶段 2 检测/发送。
录像（`RECORD_ENABLE`）时每 5 帧写一次 MJPEG，并在结束时按串口时间戳改名。

## 3. 时钟分析

- 脚本内**没有任何寄存器写入**（没有 `write_reg`、没有 PLL/时钟设置）；也没有
  `sensor.set_framerate()`（OpenMV 的该 API 只是丢帧限速，本身不改 PCLK）。
- 实际时钟来自 OpenMV 板级配置：`OMV_OV5640_XCLK_FREQ = 24 MHz`，
  `OMV_OV5640_PLL_CTRL2 = 0x64`、`OMV_OV5640_PLL_CTRL3 = 0x13`。
- 用驱动时序反推：全幅 QVGA 帧周期 1716×1000/PCLK 与 OpenMV 官方实测 46.7 fps 对应，
  得 **PCLK ≈ 80 MHz**（即"不超频"的默认配置）。
- `clock = time.clock()`（277 行）只用于 `clock.tick()`/`clock.fps()`（302/327 行），
  是软件帧率统计，不是硬件时钟。

## 4. 滤波分析

**没有滤波。** 具体：

- 检测：`img.find_blobs(LAB 阈值, roi=当前搜索区域)`，取面积最大的 blob（161-182 行）；
- 跟踪：命中后下一帧搜索 ROI = 上一帧 blob 外扩 ±40 px（185-191 行）；丢失回全屏；
- 输出：原始 blob 矩形 7 字节直发 115200 串口（194-201 行），**不发中心点、不发角度、
  不做 PnP、不做距离估计**；
- 无时间滤波/预测/限幅/融合（没有 Kalman、没有均值、没有速度项）；
- 也没有图像滤波（没有高斯/二值化/形态学），`find_blobs` 直接跑在 RGB565 上；
- 唯一的"稳定化"手段是硬件级固定：曝光 800 µs、增益 20 dB、关 AWB、预热 1.5 s。

结论：**滤波与预测全部留给接收端（飞控）**，视觉端只做"检测 + 空间 ROI"，优先延迟最小。

## 5. 采集帧数推导

OpenMV OV5640 驱动的 `set_framesize()`（v4.5.0）计算公式：

- 全幅默认（readout = 2592×1944，2× 降采样）：
  `sensor_div=2`，`sensor_w=2608`，`sensor_h=1952`
  → `HTS=max(1716, 1438)=1716`，`VTS=max(1000, 248)=1000`
  → 1716×1000 / 80 MHz = **21.45 ms ≈ 46.6 fps**（官方实测 46.7 fps 吻合）。
- 深大配置（readout = 640×480）：
  `sensor_div=2`，`sensor_w=656`，`sensor_h=488`
  → `hts_target=328`，`HTS=max(488+252, 1438)=1438`，`VTS=max(244+24, 248)=268`
  → 1438×268 / 80 MHz = **4.82 ms ≈ 207.6 fps**。

其他一致性检查：

- 曝光 800 µs：在 80 MHz、HTS=1438 下约 44 行，远小于 VTS=268，**不影响帧率**；
- 视场代价：读窗口 640/2592 ≈ 24.7%（水平）、480/1944 ≈ 24.7%（垂直），
  即线性视场只剩约 1/4（等效 4× 长焦）；输出仍是 320×240，所以目标像素更大；
- 阶段 2 用阶段 1 最后的目标 y 移动一次窗口：
  `(0, 160 + max_blob.y*2 + max_blob.h, 640, 480)`（340-341 行），
  驱动会把 y 限制在 ±(1944-480)/2 = ±732；
- 端到端 loop 帧率：代码只在 `DEBUG`/`RECORD_ENABLE` 为真时打印 `clock.fps()`
  （338 行），正式比赛配置（DEBUG=False、RECORD_ENABLE=False）不打印、不录像，
  仓库里没有实测日志。**采集侧不是瓶颈**，实际 loop 由 `find_blobs`+绘制+串口决定
  （7 B/帧 @115200 仅约 0.61 ms/帧）。

## 6. 与本板 DART H7 对比（2026-11-13 实测）

本板 OV5640 初始化为**全幅读出 + 2× 降采样**（`OV5640_Common` 表实测）：
`0x3800/01=0x0000`(HSTART)、`0x3802/03=0x0004`(VSTART)、
`0x3804/05=0x0A3F`(HEND)、`0x3806/07=0x079B`(VEND)、`0x3814/15=0x31`(2× inc)；
`OV5640_SetResolution` 只改 DVPHO/DVPVO（160×120），**HTS/VTS 仍是 1936/1088**。

今日实测（COM14，`CAMERA REGS` + `CAMERA SNAP` ×3）：

| 项目 | 深大 OpenMV（OV5640） | 本板 DART H7（OV5640） |
| --- | --- | --- |
| XCLK / PCLK | 24 MHz / ≈80 MHz（默认） | ≈12 MHz / ≈14.7 MHz（默认），PLL×2 时 ≈29.4 MHz |
| HTS / VTS | 1438 / 268 | 1936 / 1088 |
| 实际读出区域 | 640×480（2× 降采样） | 全幅 2624×1952（2× 降采样） |
| 采集帧周期 | 4.82 ms（≈208 fps 上限） | 实测 0.121–0.150 s/帧（≈7 fps） |
| 视场 | ≈24.4% × 25.0%（线性） | 100%（全幅缩放） |
| 时间滤波 | 无（ROI only） | 上位机 Kalman + PnP |
| 输出 | 7 B blob 矩形 @115200 | 1bpp/RGB565/JPEG 图像流 + 上位机解算 |
| 端到端 | 采集非瓶颈（loop 未记录） | RGB565 0.196–0.229 s（4.4–5.1 fps），1bpp 约 7.4 fps |

### 6.1 为什么本板只改 HTS/VTS 会失败（今日验证）

| 命令 | 写入结果（读回） | 结果 |
| --- | --- | --- |
| `CAMERA TIMING1`（HTS 1936 / VTS 800） | 0x380E/F=0x0320=800 ✓ | `FRAME TIMEOUT` |
| `CAMERA 60FPS`（HTS 800 / VTS 306，手动曝光 250 行） | 0x380C/D=800、0x380E/F=306、0x3503=0x03 ✓ | `FRAME TIMEOUT` |
| `CAMERA RESET` | 恢复 1936/1088 默认 | ✅ READY |

原因：**传感器仍在读全幅**。全幅 1944 行经 2× 垂直降采样后内部需要约 972 行时间，
VTS 必须 ≥ 该值（当前 1088 已接近下限）；HTS 也要 ≥ 降采样后的内部列数（2592/2 = 1296
再加消隐，约 1300+）。这个模型与当天全部失败记录吻合：

| 命令 | HTS | VTS | 是否满足内部读出下限 | 实测 |
| --- | ---: | ---: | --- | --- |
| 默认 | 1936 | 1088 | ✓ | ✅ 7 fps |
| TIMING1 | 1936 | 800 | ✗ VTS < 972 | ❌ FRAME TIMEOUT |
| TIMING2 | 1200 | 800 | ✗ HTS < 1300、VTS < 972 | ❌ |
| TIMING3/4 | 1000 | 800/612 | ✗ 两者都不够 | ❌ |
| 60FPS | 800 | 306 | ✗ 两者都不够 | ❌ |

因此**只改 HTS/VTS 必然失败**：必须先缩小 0x3800–0x3807 的读出窗口。
这也解释了此前 FAST29/FAST48（只搬 Linux 低分辨率寄存器表、未改读窗口）必然失败。

## 7. 可复制方案（读窗口 / 低 VTS）与预期

需要按 OpenMV `set_framesize()` 的方式一起写（不能只写 0x380C–0x380F）：

- 窗口：`0x3800/01` HSTART、`0x3802/03` VSTART、`0x3804/05` HEND、`0x3806/07` VEND；
- 尺寸/时序：`0x3808/09` DVPHO、`0x380A/0B` DVPVO、`0x380C/0D` HTS、`0x380E/0F` VTS；
- 偏移：`0x3810/11` HOFFSET、`0x3812/13` VOFFSET；
- 子采样：`0x3814/15`（2× 时为 0x31）、`0x3820/21` 对应位；
- FIFO：`0x4602/03` VFIFO_HSIZE、`0x4604/05` VFIFO_VSIZE；
- 曝光：切手动（`0x3503=0x03`），曝光行数 < VTS；
- 写完后按需要重新 stream on（本板已验证 `0x3008=0x42` 待机会破坏配置，不要用）。

按本板实测 PCLK ≈14.7 MHz（PLL×2 时 ≈29.4 MHz）估算：

| 读出窗口 | HTS | VTS | PCLK 14.7 MHz | PLL×2（29.4 MHz） |
| --- | ---: | ---: | --- | --- |
| 640×480（≈25% 视场） | 1438 | 264 | 25.8 ms（38.7 fps） | 12.9 ms（77.4 fps） |
| 320×240（≈12% 视场） | 1438 | 144 | 14.1 ms（71 fps） | 7.0 ms（142 fps） |

端到端（1bpp 160×120，2.4 KB，USB 约 0.9 MB/s ≈3 ms + 板上转换约 4 ms）：

| 方案 | 采集 | 传输+转换 | 合计 | 端到端 |
| --- | ---: | ---: | ---: | ---: |
| 640×480 窗口 + PLL×2 | 12.9 ms | ≈7 ms | ≈20 ms | **约 50 fps** |
| 320×240 窗口 + PLL×2 | 7.0 ms | ≈7 ms | ≈14 ms | **约 70 fps** |

注意：此前文档"60 fps 需要 PCLK≈126 MHz"的前提是 **VTS 固定 1088**；
缩小读出窗口后，60 fps 在现有 PCLK 下即可达到，代价是视场缩到约 25%（与深大相同取舍）。

## 8. 结论

1. 深大的代码**不涉及时钟超频、也没有滤波**；核心竞争力是"窄视场读出窗口 + 固定短曝光
   + 最小数据传输"。
2. 他们把 OV5640 的读出窗口压到 640×480（视场约 1/4），换到 4.8 ms/帧（≈208 fps 上限）
   的采集时序；默认全幅是 21.5 ms（≈46.7 fps）。帧率提升来自 **VTS 从 1000 降到 268**，
   不是 PCLK。
3. 本板帧率低的根因相同但方向相反：驱动只改 DVPHO/DVPVO、不改窗口/VTS，导致
   **每帧仍读全幅（VTS=1088 ≈ 972 行下限）**，所以 ≈7 fps 且只写 HTS/VTS 必失败。
4. 下一步应在本板固件实现 OpenMV 式"读窗口 + 完整时序"配置；预期采集 38–77 fps
   （640×480 窗口）或 71–142 fps（320×240 窗口），端到端 1bpp 约 50–70 fps，
   60 fps 基线可达成。
